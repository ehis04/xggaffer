EXECUTIVE SUMMARY
-----------------

The xgGaffer data automation pipeline has been fully implemented across ten phases plus
post-submission extensions. The project began with a mixed scraping, sync, file-processing
and ad-hoc command stack with no coherent answer to "what is live, who published it, when
was it published, and how does a client know if it is fresh." It now has a production-style,
scheduled, rate-limited, and observable three-layer data pipeline serving four product
surfaces across seven distinct data providers.

No existing API endpoints were broken during the migration. Every phase used a transition
flag to allow parallel operation of old and new paths before cutover.


THE THREE-LAYER ARCHITECTURE
-----------------------------

Every product surface now operates through:

1. Ingestion layer
   Scheduled, provider-specific background jobs fetch and normalise source data into
   the database. Each job records a SyncRun entry on start and completion. Provider
   execution is rate-safe, session-safe, and idempotent via Redis-backed task locks.

2. Publication layer
   After successful ingestion, a publication step validates and atomically promotes a
   candidate snapshot. The candidate is promoted only after validation passes. A failed
   publication never blanks the current active snapshot. Promotion uses
   select_for_update inside a transaction enforcing the single-active invariant.

3. Application read layer
   Views, serializers, and frontend pages read only from DB-backed published state.
   No provider calls or file reads occur on the request path (except rolling.py CSV
   reads in predictions — documented as the known remaining gap requiring a
   pre-computed feature store for full elimination).

KEY ARCHITECTURAL DECISIONS AND DEVIATIONS
-------------------------------------------

1. acquire_task_lock: silent-skip on contention, not raise
   The plan specified raising RuntimeError on lock contention. Changed to silent log-and-return
   because raising causes Celery to treat contention as task failure and trigger retries —
   defeating the purpose of the lock entirely.

2. is_provider_managed not added to Club model
   The plan specified adding is_provider_managed: BooleanField to Club. Rejected because
   Club.ClubType.SYSTEM_PROFESSIONAL already serves as the discriminator. Adding a
   redundant BooleanField creates two sources of truth. ProClubProviderLink used instead.

3. get_homepage_top_performing_teams is DB-backed
   The plan placed this behind the native_stats snapshot flag. Investigation confirmed
   it reads from CompetitionTopScorer DB model, not from native-stats HTTP. Only the
   three Playwright/HTTP-backed functions (hat_tricks, lull, all_time_streaks) are
   behind the snapshot flag.

4. FreshnessPayload.snapshot_published_at typed as string | null
   The plan typed this as string (non-nullable). The backend correctly returns null
   before the first publication — corrected in both the Python dataclass and the
   TypeScript interface.

5. TheOddsApiClient.fetch_upcoming_odds(sport_key) not OddsApiClient.get_upcoming_events()
   The odds client in the parallel feature build uses a different class name and method
   signature than assumed in the plan. fetch_task.py adjusted to match the actual interface.

6. Rolling feature computation remains on the request path
   ModelArtefactRecord and InferenceSnapshotRecord provide the publication registry
   and freshness metadata without requiring a full pre-computed feature store. Moving
   rolling.py CSV reads off the request path is a documented post-submission hardening
   step, not a defect.

7. PlayerEnrichmentSnapshot already migrated at Phase 7 start
   The model was present in playerdata/models.py and migration 0004 was already applied.
   No action needed in Step 1 of Phase 7.

8. refresh_native_stats_cycle_task does not open its own SyncRun
   The cycle task dispatches refresh_livefootball_native_stats which owns its own SyncRun.
   Opening a second SyncRun in the cycle task would create duplicate tracking rows.
   The cycle task only acquires the lock and dispatches.

9. WhoScored players uses read_player_season_stats(), teams uses read_team_season_stats()
   soccerdata's WhoScored class exposes season-level aggregates via these methods rather
   than the match-level read_schedule() used for matches. This mirrors the SofaScore
   pattern where teams uses read_league_table() rather than read_schedule().

10. Transfermarkt DOB fetch is outside the PlayerExternalIdentity transaction
    The identity upsert is wrapped in transaction.atomic(). The profile HTTP fetch for
    DOB is intentionally outside this transaction to avoid holding a DB lock across a
    network call. If the fetch fails, the identity record is still committed.

   Papertrail, or file handler) requires settings.LOGGING configuration.

2. Frontend envelope adoption for remaining surfaces
   playerdata views, clubs views, remaining predictions views (simulate, availability,
   lineup, odds) still return raw <T>. The pattern is established in Phase 9.

3. useFreshData hook
   Deferred nice-to-have from Phase 9. Enables tab-visibility refetching across surfaces.

4. Pre-computed feature store for predictions
   Moving rolling.py CSV reads off the request path. ModelArtefactRecord and
   InferenceSnapshotRecord provide the registry; a feature pipeline job provides the data.

5. Odds/betting unit tests
   fetch_and_persist_odds has no unit tests — requires mocking TheOddsApiClient.
   ODDS_API_ENABLED=False in dev made these impractical during implementation.

6. Rate limiting for /internal/ endpoints
   Three health endpoints have no rate limiting beyond IsAdminUser. Appropriate for
   production deployment.

7. Transition flag removal
   Three surfaces still have USE_PUBLISHED_* flags set to False (predictions, playerdata,
   clubs). After confirming parity in staging, flags and old read paths can be removed.

8. WhoScored dedicated test coverage
   WhoScored extractors and transformers follow the same structure as SofaScore but have
   no dedicated test file. test_whoscored_transformers.py should be added mirroring
   test_sofascore_transformers.py.

9. Transfermarkt name reconciliation
   _find_or_create_player() currently matches by exact name (case-insensitive). A fuzzy
   match or cross-reference via PlayerExternalIdentity would reduce stub player creation.

10. Deployment process manager
    In production, each Celery worker and Beat should be managed by systemd or supervisor
    rather than start_workers.sh. start_workers.sh is a development convenience only.
